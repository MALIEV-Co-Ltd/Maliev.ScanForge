# SpaceMouse input

Supported SpaceMouse devices exposed through the browser Gamepad API are detected automatically. Some browsers expose a device only after the cap moves or a button is pressed. Detection uses supported device IDs or model names and requires six axes; generic game controllers are ignored. Finite values outside ±1 are saturated by the shared motion filter. Nonfinite samples are skipped while polling continues; neither condition means the device disconnected. The header control opens navigation settings and shows a pulsing connected indicator.

**Connect via 3Dconnexion** explicitly connects to the installed 3DxWare driver. It loads the separately licensed SDK only when requested. Windows requires 3DxWare 10.9.9 or later; macOS requires 10.8.10 or later. The driver exchanges absolute camera poses and manages its own sensitivity. Gamepad input pauses while the driver owns navigation and resumes after driver disconnection. Failed or cancelled connections release discovery requests, pending transports, retry timers and viewport listeners. Discovery has an eight-second deadline; driver readiness has a ten-second deadline.

Browser HID remains a fallback in Settings. Its chooser requires a user click, WebHID support and a secure context (HTTPS or localhost). Startup and **Use automatic** try Gamepad first, then reopen a previously authorized HID device when Gamepad is absent; they never open the permission chooser. **Disable navigation** stops input until a connection or automatic detection is enabled again. These choices do not modify model history.

Supported report layouts cover SpaceNavigator, SpaceMouse Pro, Compact, Wireless, Pro Wireless and the Universal Receiver. An allowlist restricts product/vendor IDs. Signed six-axis reports drive camera-relative translation and rotation about the orbit pivot. Device buttons map to fit/isometric views when present. Settings adjust translation/rotation speed, deadzone, dominant-axis mode and rotation lock. Both speed controls default to 1. These preferences are session-local.

Split and combined input layouts, invalid/truncated reports, button rising edges, stale-input expiry, disconnect and permission/open races are covered by synthetic HID tests. Camera tests cover translation, orbit radius, finite inputs and elapsed-time bounds. Physical-device axis direction, driver interaction, receiver routing and browser permission behavior require real hardware testing and have not been verified. An installed emulator does not prove a physical device works.

HID motion expires after 150 milliseconds without fresh reports. Background pages ignore automatic input; the Gamepad loop stops while hidden or disconnected. Disconnect, page exit and component cleanup remove listeners and close only connections opened by this controller. Physical Gamepad axis direction and official driver navigation still require hardware validation.

Protocol decisions use the public [WebHID specification](https://hid.spec.whatwg.org/) and [3dmouse-hid device report inventory](https://github.com/hcrlab/3dmouse-hid). The implementation is independently authored. Browser/OS policies can restrict access to devices; unknown devices are rejected rather than decoded speculatively.

The continuation validation adds a combined synthetic workflow from explicit HID selection/open through six-axis reports, camera movement, button callbacks, stale expiry and disposal. It verifies software routing and resource release, not physical hardware. A fresh Windows PnP inventory on 12 October 2026 detected a healthy SpaceMouse Pro HID device (`046d:c62b`), replacing the earlier emulator-only inventory. This proves OS enumeration; browser permission, incoming physical reports and camera navigation remain separate validation steps.

HID chooser results may contain multiple interfaces for one physical device, as described by the [WebHID requestDevice contract](https://hid.spec.whatwg.org/#dom-hid-requestdevice). The controller selects a supported interface containing motion report IDs 1/2, skipping button-only interfaces. Device descriptors absent from synthetic fixtures retain the original allowlist fallback. Axis reports are accepted in split six-byte and combined twelve-byte packets. Connection status distinguishes an open device waiting for reports from the first successfully decoded motion report, and does not trigger UI updates on every packet. A waiting status alone does not prove navigation works. Permission belongs to the browser profile and exact origin; access granted in a different browser or port does not authorize this preview.
