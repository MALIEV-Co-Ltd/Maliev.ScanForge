# Native Interactive mirrored-point rendering

The [trace index](evidence/interactive-mirror-point-native-trace.json) binds the original image hashes, retained REA/Ghidra evidence and renderer dispatch. This is internal rendering groundwork; the public Interactive command remains gated.

## Dispatch and recovered rules

Original mirror callback `0x14069e900` snapshots each mesh style, sets the base RGBA to `(Float32(0.8), Float32(0.8), 0, 1)`, selects mode 2 and point size 2, calls renderer `0x140836100`, and restores the style. The renderer's embedded object at `+0x280` is initialized by `0x140ac9070` with vtable `0x141269518` (`cM2SMeshGLRenderer`). Its `+0x8` dispatch is `0x1408c00f0`; mode 2 selects slot `+0x18`, original point loop `0x1408c04e0`.

The point loop submits `GL_POINTS` and applies these rules in order:

- Skip vertex flags masked by `9` (bits 0 and 3).
- In selected-only mode, require flag bit 1.
- Apply the separate stride field when its signed 32-bit interpretation is at least 2. The modulus uses the unsigned field. High-bit values therefore take the original all-points branch.
- An unselected candidate changes the current GL color before normal culling. A selected candidate inherits the current color; the loop does not restore the initial selected color for every selected vertex.
- Unless backfaces are enabled or the view direction is zero, require a positive Float32 dot product. Products and additions are rounded in native Y/X/Z order. The original comparison rejects unordered products, including overflow cancellation from otherwise finite inputs.
- With zero view direction, multiply both colors by Float32 `1.8`, rounding and clamping their upper components to 1.

The argument `1,000,000` passed by the mirror wrapper is **not a one-million-point cap**. The point loop compares it with elapsed milliseconds after submitting all eligible points. A smaller allowance changes its completion flag, without truncating the point list. The wrapper also has an equality check for this value; that check does not establish a point limit.

## Shared background preparation

`InteractiveBoundsPool.mirror` now runs the recovered point loop in the same pool used for measured bounds. A session owns at most two physical workers. Concurrent bounds and mirror requests share one source preparation per worker; original position, normal and flag buffers remain attached. A failed worker generation cannot terminate its replacement through a late error event. Explicit cancellation permanently closes the pool, and idle/request/self leases remain bounded.

Partitioning preserves global stride indices and the original color-state transition across worker boundaries. Each partition receives whether an earlier eligible unselected vertex changed the current color, including candidates rejected by normal culling. The optional source-indexed color output stores candidate colors before normal culling, allowing the renderer to retain colors while view direction changes. Colors must be rebuilt when flags, stride, selected-only mode, RGB values or zero-direction brightness change. An indices-only request returns no color buffer. Worker failure or unavailability uses a cooperative fallback with at most 32,768 points per task, rather than processing the whole scan synchronously.

The [owner-source native capture](../tests/fixtures/interactive-owner-mirror-points-native.json) executes the complete original point loop over all 3,381,455 source vertices from the three supplied PLY scans. It records deterministic test flags, source-file/coordinate/normal/flag hashes, and native index/color/submitted-position hashes. These are the same buffers and recorded test selections supplied to the port; they do not establish native importer parity or the native UI's facet-selection mapping.

The [real-worker browser replay](evidence/interactive-mirror-background-browser.json) matches those three native output digests and all 2,160 smaller native cases. It also retains the 99 bounds-kernel and 18 owner PLY/ASC pose comparisons. Bounds followed by mirror preparation reuses the same cached worker sources. Fifteen warm, changing-direction requests transfer indices only, without new source preparation or color arrays. Those requests measured approximately 3–23 ms, with no observed main-thread long tasks during the short warm-update sample. At most two workers were live, and zero remained after close. These are preparation timings, not complete rendering or native application timings.

This backend remains internal. The public Interactive dialog, App integration of mirrored GPU display, actual native UI selection mapping and end-to-end GUI/MCP publication are still unfinished. No unsupported public descriptor or enabled ribbon command is introduced by this checkpoint.

## Camera-to-mirror and GPU presentation

REA resolved renderer vtable `0x1411ed858`, slot `+0xf0`, to original `0x140833570` (Evidence `ev_d417b571c8f58a9ba5096de43e189d1f441a263309696795f418d3472ccfc1b8`). It unprojects a point by subtracting view-frame translation, multiplying by the transposed basis, and adding the view anchor. Its Z sum retains Y-before-X order. This is the original transpose operation, not a general matrix inverse.

Original `0x140836100` calls that adapter for `(0,0,0)` and `(0,0,1)`, converts each endpoint to Float32, and only then subtracts them in Float32. It does not normalize the direction or rotate it through each object's pose/reflection. A large anchor can cancel the direction entirely, selecting the already-verified zero-direction brightness/culling branch. The application preserves this behavior in `interactive-mirror-view.ts`. Replacing it with a normalized camera axis would change output.

The [pipeline capture manifest](../tests/fixtures/interactive-mirror-pipeline-native.manifest.json) binds 48 original unprojection results and 288 complete original renderer calls, varying four view frames, four anchors, three object poses, three reflection planes and backface state. The controlled renderer interfaces supply frame/anchor getters, styles, an initialized epoch, GL matrix sinks and an embedded draw boundary. The original unprojection, Float32 direction stores/subtractions and object-pose conversion execute unchanged. The fixture also retains the earlier 24-case wrapper capture. Tests compare Double point bytes, Float32 direction bytes, Float32 column-major object poses and the wrapper's emitted Double reflection matrices. These captures do not use a real native window or GL context.

`InteractiveMirrorDisplay` is the GPU presentation sink for the shared pool's prepared results. It uses the original origin reflection as a parent matrix, followed by each object's Float32 pose. Position/normal attributes reference immutable source buffers. A capacity-sized dynamic index attribute is reused for subsequent point lists; colors retain their attribute/buffer unless a new color configuration is supplied. Pose updates do not rebuild geometry, normals, bounds or point lists. Frustum culling is disabled for these disposable preview points to avoid an implicit first-frame bounds scan; session bounds remain authoritative.

The presenter compiles point materials asynchronously, then stages source uploads one scan per frame into a disposable 1px render target before revealing the group. Each upload restores the previous render target, cube face/mipmap level, viewport, scissor and scissor-test state. Logical canvas defaults are restored before rebinding an offscreen target, which retains its own physical viewport/scissor. Clear/Dispose invalidates pending preparation and wakes bounded frame waits; late completion cannot reveal a cancelled group. Removed materials remain alive until active asynchronous compiler polls stop reading them, then dispose exactly once. The caller owns the shared pool/session. The presenter owns and disposes only its preview geometries/materials and temporary render target.

The [three-PLY WebGL replay](evidence/interactive-mirror-gpu-buffer-browser.json) retains native index/color/submitted-coordinate hash comparisons and renders 329,983 prepared points across three GPU objects. These short local measurements do not establish overall application or native performance parity.

The point material uses the application's unlit point presentation with size 2, fixed screen size and prepared vertex colors. Native fixed-function lighting and pixel-identical output remain unverified. Full viewport/App ownership, native UI facet-to-vertex selection mapping, CAD handling, complete dialog admission, public schemas/discovery and GUI/MCP Apply/Cancel/Undo still require integration and validation. ## Native facet display state and session source ownership

Original `0x14088aeb0` (REA evidence `ev_d4a126dea9cad71c3553471d2bc9b0fb4b302ba11fc189d031fb4916a289a551`) prepares vertex display flags once. A ready entity returns before accessing its faces or vertices. A fresh entity clears vertex bit 2 and sets bit 8; visible faces clear bit 8 on their corners, while visible selected faces set bit 2. Hidden faces contribute to the hidden summary but do not change corner flags. Other vertex bits survive. The routine records selected/hidden summaries, visible face count and readiness. It performs no vertex welding and does not compute normals.

The native capture contains 4,100 controlled original executions, including cached re-entry without getter calls. A second capture runs the same original routine on all three owner PLY scans, with facet selection `i % 17 < 3` and hidden facets `i % 23 == 0`. Those original vertex flags then enter the original mirrored-point routine. The [owner face-state fixture](../tests/fixtures/interactive-owner-face-state-native.json) records source, triangle, flag, index, color and submitted-coordinate hashes. This establishes the two original routines' behavior on the same complete input buffers and recorded selection. Native importer seed flags, native UI selection retention, native lighting and full-window pixel parity are not established.

`interactive-mesh-source.ts` implements the recovered flag preparation. The existing session bounds pool owns source preparation and mirrored-point work, with at most two physical workers and a 512 MiB source budget. Concurrent bounds/display requests derive a source once. Worker idle expiry preserves the host's prepared metadata; closing the session clears it. Existing PLY normals are retained. Missing normals use the existing angle-weighted helper in the worker; its use as the original STL importer's normal producer remains unverified. Without workers, large missing-normal requests are rejected instead of blocking the main thread. Cooperative flag preparation remains available.

A session-owned `InteractiveMirrorBackend` lends immutable source buffers and prepares draw indices through that same pool. Its optional host callback, source summaries and release path are shared application-operation groundwork. Session identity and unchanged author state are checked around asynchronous preparation. No public Interactive descriptor or ribbon enablement is added here; the App/viewport consumer and complete GUI/MCP publication remain unfinished.

## Viewport mirror request controller

`InteractiveMirrorController` connects the existing session backend to the GPU sink without owning another worker pool. It permits one active preparation request and retains the latest pending view. Results from an obsolete view, cancelled preview or disposed display are not published. Matrix-only pose and reflection changes update the display immediately without scanning or transferring source vertices. Identical requests do not invalidate the canvas, allowing the viewport to become idle.

Color reuse follows the verified point-loop dependencies: flags/source identity belong to the immutable session, while stride, selected-only filtering, RGB values and the zero-direction brightness branch determine source colors. Changing a nonzero culling direction or backface setting reuses colors. A failed multi-target preparation cannot make a partially changed display appear ready; returning to the preceding view restores any changed draw lists. Failures remain bounded diagnostics rather than retrying every animation frame.

The viewport borrows this controller through `installInteractiveMirror`, forwards the recovered Float32 direction from the current captured camera, and disposes GPU objects on cancellation/replacement. It retains the application's selected-facet tint. The original fixed-function lighting and native UI style/pixel parity remain unverified. The existing `viewport_get` operation forwards structured readiness/failure diagnostics from the viewport. The complete App/dialog connection and public Interactive activation remain pending; no unsupported ribbon command or Interactive operation descriptor is enabled by this checkpoint.
