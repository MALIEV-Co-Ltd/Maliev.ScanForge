scan-frame preview/apply workflow is available in Object properties and MCP;

## Verified cone apex, axis and axial range

The native model setter at `0x1404dd080` stores origin at `0x30`, normalized
axis at `0x48`, opening half-angle at `0x60`, axial start at `0x68` and span
at `0x70`. Its endpoint routine `0x1404dc670` returns origin plus axis times
start, origin plus axis times start-plus-span, and the origin itself.
The signed-distance routine `0x1404dd1c0` measures positive axial coordinates
away from this origin and uses `cos(angle) * radial - sin(angle) * axial`.
Thus the origin is the apex and the axis points outward from it.

`src/scan-native-datum-cone.ts` converts authored fit metadata into the same
geometry. For unit base-to-small-end axis A, base center C, radii R > T >= 0
and height H, the apex is `C + A * R * H / (R - T)`, outward axis is `-A`,
start is `T * H / (R - T)` and half-angle is `atan((R - T) / H)`.
Zero-height, cylindrical and inverted-radius inputs are rejected rather than
assigned an invented apex. The original endpoint arithmetic is ported directly.

`alignment-datum-cone-native.json` retains 48 original endpoint/distance
executions covering true cones, truncated cones, oblique axes and the six
principal directions. Tests restore the original axis bytes because JSON
module transforms can erase signed zero. All handle and direction bytes must
match; native handles must also land at the authored small/base centers within
`1e-12 mm`. Half-angle agreement uses `1e-15` tolerance across math libraries.
The original distance routine evaluates 228 authored lateral-surface samples;
maximum absolute residual is `2.220446049250313e-14 mm`. Apex samples are
excluded from that distance check because the original routine's near-zero
axial guard returns its invalid-distance sentinel there. The apex remains a
valid point reference through the original feature converter.

## Bounded application transform scheduling

The origin/reference operation now applies the verified native worker arithmetic through a bounded CPU executor. Large streams admit two workers; small scans, explicit serial requests and unavailable/low-memory worker environments use serial chunks. Logical chunk ordering is retained regardless of response order. The same native fixtures are replayed through transferable tasks and cover output bytes, source ownership, partial tails, cancellation and worker cleanup. This scheduling choice is an application implementation: the native complete controller and its original ConCRT thread scheduling have not yet been replayed for this transform. GPU arithmetic remains unimplemented because its precision requires a separate parity gate.

The actual Chrome-worker validation replayed all 1,104 native captures and compared every coordinate of the three full-resolution owner STL scans between worker and serial execution, including a nontrivial rotation/translation. File digests matched the retained input identities. The final tested streams contained 819,417, 7,642,215 and 9,980,730 vertices. The smaller stream used the automatic serial path; the other two admitted two workers. Six transform workers were created and all six terminated. This is full coordinate-output comparison against the native-verified serial kernel; it is not a complete native controller, import or registration/merge replay.

On one admitted 16-thread Chrome run, coordinate transformation plus bounds collection took approximately 22, 123 and 223 ms. These timings exclude import, indexed-mesh validation, normal streams and viewport updates; they vary with machine load and allocation. The synchronous coordinate-plus-bounds baseline took approximately 18, 112 and 243 ms. Multicore is therefore primarily a responsive, cancellable path here, not a guaranteed raw speedup on every scan. Preserving Float32 transport and fusing bounds/validation removed avoidable copies and passes. Performance receipts remain in the task resource artifacts; no production deployment is implied.

## Exact-CAD Apply recovery

The CAD-model transform at `0x14049faa0` forwards the matrix to each body's transform slot. Body `0x1404982c0` first transforms its embedded exact-shape record through `0x140283b30`, then refreshes derived geometry and display data. The OpenCascade branch calls `0x1401eb560`. This helper inverses the incoming matrix, normalizes its first and third columns as directions, orthogonalizes the X direction with a normalized triple cross product, constructs Y with a normalized cross product, and calls `gp_Trsf::SetTransformation(gp_Ax3)`. The intermediate inversion does not imply that CAD geometry moves in the opposite direction: the axis-frame conversion provides the final placement transformation.
